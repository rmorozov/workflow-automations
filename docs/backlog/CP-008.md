# CP-008 Capacity and estimate measurement contract

From the [model review on PR #48](https://github.com/rmorozov/workflow-automations/pull/48#issuecomment-6292432126). Settle the issue; a full forecasting system is not in scope.

Capacity hours, execution hours and estimated-work hours are compared without an
explicit conversion contract. Define what change-request estimates (`RemainingWork`)
and logged work include: unit tests, debugging, integration, review responses,
pre-acceptance defect correction and production support. Define whether a parent's
value summarizes its children or is extra effort. A Bug type alone cannot tell
production support from feature rework that was already estimated. Record each
team's convention in the config (or reject unsupported ones) instead of assuming
they are comparable, and state the unit of every output column.

This is the prerequisite for operational use: settle it before tuning any rate,
because a percentage tuned to fit incompatible units hides the mismatch.

## Acceptance evidence

A work-category accounting table in the spec, with worked examples showing each
activity counted once on the demand side and once on the capacity side; explicit
units for every output; how the code-review deduction changes when a team's
estimates already include review; team conventions represented in the config or
clearly rejected, with a test for each.
