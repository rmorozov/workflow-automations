# CT-010 CI verdict from per-repo, per-branch Gerrit labels

Design: [cycle-time specification](../specs/cycle-time.md). Ruslan (2026-11-24): CI
validation is a set of labels on the review (build, test, linters and so on), and which
labels exist is defined per repo per branch.

Today the CI verdict is a pipeline result, matched to a revision through `tested` and
queue-time rules. Gerrit votes are already bound to a patchset, so read the verdict from
them instead:

- Each change has a `branch`; a `vote` event has a `label` (default Code-Review) and the
  patchset it was cast on.
- Each change lists the labels it needs to be submitted, as Gerrit reports them for that
  change (they reflect repo and branch). A rules file keyed by repo and branch pattern can
  supply or override them for fixtures and history.
- A change passes CI when every required CI label is at its maximum on the current
  patchset; a topic passes when every change passes its own set. A negative CI label is
  author time only when a new patchset follows it (see below).
- Builds only explain queue and run time. A CI wait span lists the labels still missing,
  and the trace gets one lane per label.

Ruslan's answers (2026-11-24):

- Nothing is build-validated without a topic attached to one or more reviews, so a build
  always belongs to a topic.
- Many pipelines can put labels on a change; each sets one or more labels (some fan out
  from one entry point). Every repo has a common subset of mandatory labels, plus extra
  labels configured per repo per branch. So required labels = global mandatory set +
  (repo, branch) extras, and builds map to labels many-to-many.
- Infra failures hide inside other labels: a −1 can't tell a network failure from a real
  one. So a −1 is classified by what follows it: a new patchset makes the time since the
  −1 `rework`; a re-run on the same patchset makes it a gate kind (`ci_retry`), because
  nobody changed the code. Until either happens it is `ci_failed` (unresolved). Log
  mining from the build-log share (CT-004) can refine this later.

- CI labels reset on every new patchset; only a Code-Review −2 is kept (implemented).

## Status

The first slice is on PR #56: label rules, the label verdict, `ci_retry` and `ci_failed`,
scenario `25_ci_labels`. Still to do: list the missing labels on a CI wait span, one trace

## Acceptance evidence

Scenarios with two repos on different branches and different label sets: the topic waits
until the last required label of the last change arrives; a −1 lint label followed by a
new patchset is rework; a
label from the previous patchset does not count; a −1 followed by a re-run on the same
patchset is `ci_retry`, not rework; a repo with an extra label waits for it.
