# CT-010 CI verdict from per-repo, per-branch Gerrit labels

Design: [cycle-time specification](../specs/cycle-time.md). Ruslan (2026-11-24): CI
validation is a set of labels on the review (build, test, linters and so on), and which
labels exist is defined per repo per branch.

Today the CI verdict is a pipeline result, matched to a revision through `tested` and
queue-time rules. Gerrit votes are already bound to a patchset, so read the verdict from
them instead:

- Each change has a `branch`; a `vote` event has a `label` (default Code-Review) and the
  patchset it was cast on.
- Each change lists the labels it needs to be submitted, as Gerrit reports them for that
  change (they reflect repo and branch). A rules file keyed by repo and branch pattern can
  supply or override them for fixtures and history.
- A change passes CI when every required CI label is at its maximum on the current
  patchset; a topic passes when every change passes its own set. A negative CI label is
  author time.
- Builds only explain queue and run time. A CI wait span lists the labels still missing,
  and the trace gets one lane per label.

Open (asked 2026-11-24): one pipeline per label or one for several; whether any CI label
survives a new patchset (copy conditions); whether infra failures can set a CI label to −1.
Defaults until answered: labels reset on every new patchset, any −1 is author time, one
build may set several labels.

## Acceptance evidence

Scenarios with two repos on different branches and different label sets: the topic waits
until the last required label of the last change arrives; a −1 lint label is rework; a
label from the previous patchset does not count.
